# 스마트 횡단보도 — 보행자 잔류 감지 기반 신호 연장 + 쓰러짐 감지

라즈베리파이 카메라로 횡단보도를 지켜보며 두 가지를 판단한다.

1. **아직 다 건너지 못한 사람이 있는가** → 보행 신호를 연장한다
2. **쓰러진 사람이 있는가** → 부저를 울린다

판단은 라즈베리파이가 하고, 신호등·부저·7세그먼트 제어는 아두이노가 한다.

---

## 설계의 중심 원칙

**각자 자기만 아는 것을 판단한다.**

| | 아는 것 | 판단하는 것 |
|---|---|---|
| **라즈베리파이** | 영상, 사람 위치, 진입 방향 | 잔류 확정, 쓰러짐 확정, 가장 덜 건넌 사람이 몇 번째인가 |
| **아두이노** | 잔여 녹색 시간(7세그먼트) | 얼마나 연장할까, 누적 상한, 사이클 리셋, 부저·LED |

"남은 시간이 5초 미만인가"는 카운트다운을 소유한 아두이노만 답할 수 있고, "이 사람이 몇 번 구역에 있는가"는 영상을 보는 파이만 답할 수 있다. 그래서 파이는 **"무엇을 보았는가"만 보내고**, "언제 얼마나 연장할까"는 아두이노가 정한다.

이 분리 덕분에 파이는 잔여 시간을 몰라도 되고, 아두이노는 영상 처리를 몰라도 된다. 주고받는 메시지도 한 줄로 줄었다.

## 동작 원리

### 카메라 구도와 기준점

카메라는 **보행자 신호등에 부착되어 횡단보도를 사선으로 내려다본다**(탑뷰 아님).

사람의 위치는 bounding box **중심이 아니라 아래쪽**을 기준으로 잡는다. 중심점은 사람 키의 절반만큼 떠 있어서, 사선 각도에서는 실제 서 있는 지점보다 카메라 쪽으로 당겨진 위치로 잘못 판정된다.

정확히는 박스 하단에서 높이의 10%만큼 올라온 지점을 쓴다(`FOOT_POINT_OFFSET_RATIO`). 검출 박스가 발밑보다 조금 아래까지 잡히는 것을 보정한 값으로, 픽셀이 아니라 **비율**이라 멀리 있는 사람도 같은 비율로 보정된다.

### 5구역 — 화면이 아니라 실거리로 나눈다

횡단보도를 걷는 방향을 따라 5개 구역으로 나눈다.

```
진입 끝 ┃ 1 │ 2 │ 3 │ 4 │ 5 ┃ 반대 끝
        └───┴───┴───┴───┴───┘
```

**화면상 균등 분할은 실제로는 전혀 균등하지 않다.** 사선 구도에서는 먼 쪽 1픽셀이 가까운 쪽 1픽셀보다 훨씬 긴 거리를 나타내기 때문이다. 그대로 두면 횡단보도의 진짜 한가운데가 3번이 아니라 4번 구역에 들어간다.

그래서 네 꼭짓점과 실제 치수로 **호모그래피**를 만들어 평면 좌표(cm)에서 5등분한 뒤 픽셀로 되돌린다. 체스보드 카메라 캘리브레이션은 필요 없다 — 보행자의 발은 지면이라는 **평면 하나** 위에 있으므로 사영변환만으로 원근이 펴진다.

### 구역 번호가 아니라 '진척도'를 보낸다

구역 번호를 그대로 보내면 **진입 방향에 따라 의미가 뒤집힌다.** 물리적으로 같은 2번 구역이라도, 1번 쪽에서 들어온 사람은 대부분 남았고 5번 쪽에서 온 사람은 거의 다 건넜다.

그래서 파이가 track별 진입 방향을 보정해서 항상 같은 뜻으로 통일해 보낸다.

```
진척도 1 = 방금 진입          진척도 5 = 거의 다 건넘
```

방향은 **첫 검출 구역**으로 판별한다(속도를 쓰지 않으므로 프레임률 요구가 없다). 중앙에서 처음 보이면 아직 모르는 것으로 두고, 이후 구역이 바뀌는 방향으로 확정한다.

여러 명이면 **가장 작은 값**(가장 덜 건넌 사람)만 보낸다. 기준표가 단조 감소이므로 그 사람이 항상 가장 부족하고, 나머지는 볼 필요가 없다.

### 잔류 확정과 검출 끊김 대응

검출 흔들림 하나로 신호가 오락가락하면 안 되므로, 횡단보도 안에서 **연속 몇 프레임** 검출돼야 '확정 보행자'로 본다(`ZONE_RESIDENCY_FRAMES`).

YOLO는 가림·모션블러에서 한두 프레임씩 사람을 놓치는 것이 정상이다. 그때마다 카운트를 0으로 되돌리면 확정 보행자가 좀처럼 나오지 않고, **에러 없이 조용히 연장만 빠진다.** 그래서 두 겹의 대응을 둔다.

- **미검출 유예**(`TRACK_GRACE_FRAMES`) — 몇 프레임 안 보여도 상태를 지우지 않는다. 다만 안 보이는 동안 카운트는 **동결**한다(잔류의 증거가 없으므로 올려주지도, 뺏지도 않는다).
- **track_id 재발급 상속**(`TRACK_INHERIT_DISTANCE_CM`) — 추적기가 같은 사람에게 새 ID를 주면, 직전에 사라진 트랙의 발 위치 근처에 나타난 새 ID를 같은 사람으로 보고 상태를 물려준다.

두 번째가 특히 중요하다. 상속이 없으면 새 ID는 **진입 방향을 모르는 상태**가 되어, 거의 다 건넌 사람(구역 4)이 "방금 진입"(진척도 2)으로 보고되고 진척도가 오히려 감소하면서 연장이 계속 다시 붙는다.

단, **'구역 밖으로 나감'은 유예 대상이 아니다**(즉시 리셋). "안 보임"은 정보가 없는 상태지만 "밖으로 나감"은 확실한 정보다. 둘을 같이 취급하면 이미 건너간 사람 때문에 차를 세우게 된다.

### 쓰러짐 감지

같은 프레임, 같은 추론 결과를 쓴다. 포즈 모델(`yolov8n-pose`)의 키포인트에서 **어깨 중점 → 엉덩이 중점** 벡터가 수직에서 얼마나 기울었는지 본다.

키포인트 신뢰도가 낮으면(모형이 작으면 흔하다) bounding box의 **가로/세로 비율**로 폴백한다.

판정은 시간 기반이지 프레임 기반이 아니다. 저 FPS에서도 성립해야 하기 때문이다.

- **발동**: 쓰러짐 후보가 일정 시간 유지되면 확정. 짧은 미검출은 무시하고 카운트를 이어간다.
- **해제**: 확정 이후 '정상 자세 또는 횡단보도 이탈'이 연속으로 유지돼야 해제한다. 깜빡임으로 사이렌이 꺼지지 않는다.

### 추론은 프레임당 한 번뿐이다

신호 연장과 쓰러짐 감지가 각자 YOLO를 돌리면 **FPS가 그대로 반토막 난다.** 실측상 추론이 프레임 시간의 99.6%(82.4ms vs 나머지 0.35ms)를 차지하기 때문이다. 그래서 한 번 검출한 결과를 두 판정에 나눠 준다.

## 시리얼 프로토콜

개행으로 끝나는 ASCII 한 줄. 보드레이트는 `SERIAL_BAUDRATE`(현재 115200)이며 **아두이노 스케치의 `Serial.begin()`과 반드시 같아야 한다.**

| 파이 → 아두이노 | 의미 |
|---|---|
| `normal` | 횡단보도에 확정 보행자가 없음 |
| `zone1` ~ `zone5` | 가장 덜 건넌 사람의 진척도 |
| `fall` | 쓰러짐 확정 |
| `PING` | 연결 확인 |

| 아두이노 → 파이 | 의미 |
|---|---|
| `READY` | 부팅 완료 (파이가 이걸 기다린 뒤 전송을 시작한다) |
| `PONG` | `PING`에 대한 답 |

상태는 **소문자**이고 `zone` 뒤 숫자는 **붙여 쓴다**(`zone2`, `zone 2` 아님).

### 전송 정책

**상태가 바뀔 때 즉시, 그리고 1초마다 한 번 더** 보낸다.

- 매 프레임 보내지 않는 이유: 초당 수십 줄을 밀어 넣으면 아두이노의 수신 버퍼가 넘치고, 응답까지 하면 그 송신 시간에 아두이노 루프가 묶인다.
- 그럼에도 재전송하는 이유: 변화 시에만 보내면 그 한 줄을 놓쳤을 때 아두이노가 **영영 옛 상태로 남는다.** 주기적 재전송이 유실을 자동 복구하고, 아두이노는 이걸 워치독으로도 쓸 수 있다("N초간 아무것도 안 왔다 → 파이가 죽었다").

### 아두이노 쪽 구현 시 주의

**① 기준표는 하드코딩하지 말고 계산할 것.**

```c
float base(int n) { return GREEN * (1.0 - (2.0*n - 1) / (2.0*N)); }
// 녹색 10초 / 5구역 -> 9, 7, 5, 3, 1
```

"정상 속도로 걸었다면 n번째 구역에 도착했을 때 이만큼 남아 있어야 한다"는 뜻이다. **이 표가 정상 보행 속도를 담고 있어서** 파이가 속도를 잴 필요가 없다. 느린 사람은 기준 대비 지연이 크게 잡혀 자동으로 더 연장받으므로, **교통약자를 따로 검출할 필요도 없다.**

**② 연장은 조금씩 나눠서.** 크게 한 번 주면 보행자가 곧바로 건너가도 되돌릴 수 없다. 낭비의 상한이 곧 1회 연장량이다. 매번 지연을 다시 재는 피드백 루프가 되어, 뛰어가는 사람은 다음 구역에서 연장이 자연히 줄어든다.

**③ 부저는 `fall`일 때만 켤 것.**

```c
buzzerOn = (lastState == "fall");   // fall이 아닌 모든 상태 = 끔
```

`normal`을 기다리면 안 된다. 쓰러진 사람이 일어나 횡단보도에 그대로 있으면 파이는 `fall` 다음에 곧바로 `zone`을 보낸다 — 여전히 확정 보행자이기 때문이다.

```
zone1 → zone3 → fall → zone4
                        ↑ normal이 끼지 않는다
```

`normal`은 "쓰러짐 해제"가 아니라 **"확정 보행자 없음"**이다.

**④ 부팅 시 `Serial.println("READY")`.** 자동으로 나가지 않으니 `setup()` 끝에 직접 넣어야 한다. 없으면 파이가 연결 확인에 실패하거나 시작이 느려진다.

## ⚠️ 지금 수치는 모형 기준이다 — 실제 횡단보도에는 조정이 필요하다

이 저장소의 값들은 **축소 모형(폭 19cm × 길이 29.2cm)** 에서 실측·조정한 것이다. 실제 횡단보도에 적용하려면 아래를 다시 정해야 한다.

### 반드시 다시 재야 하는 값

| 값 | 지금 (모형) | 실제 적용 시 |
|---|---|---|
| `CROSSWALK_REAL_WIDTH_CM` / `LENGTH_CM` | 19 / 29.2 | 실제 횡단보도 치수(cm). 이 값이 호모그래피와 구역 분할 전체를 결정한다 |
| `TRACK_INHERIT_DISTANCE_CM` | 8.0 | **구역 하나의 길이보다 작아야** 한다. 넘으면 옆 구역의 다른 사람을 같은 사람으로 잇는다 |
| 아두이노 `GREEN`(기본 녹색) | 데모용 짧은 값 | 실제 신호 주기 |
| 아두이노 1회 연장량 / 누적 상한 | 데모용 | 국내 운영 사례는 1회 3~6초, 누적 5~10초 범위 |

### 축척 때문에 성립하는 관계

모형은 실제 횡단보도의 축소판이므로, **거리만 줄이면 시간이 맞지 않는다.**

```
시간 축척 = 거리 축척 ÷ 속도 축척
```

즉 모형 보행자를 **실제 보행 속도와 같은 비율로** 느리게 움직여야 시간 축척이 1:1이 되어, 연장 초의 실제 운영 사례 값을 그대로 쓸 수 있다. 모형이 그보다 빠르면 시간 축척만큼 연장 초를 나눠야 한다.

**실제 횡단보도에서는 이 축척 보정이 통째로 사라진다** — 사람이 실제 속도로 걷기 때문이다. 통과 시간은 `횡단보도 길이 ÷ 보행 속도`로 직접 계산하면 된다(국내 기준 1.0 m/s, 교통약자 0.8 m/s).

### 카메라 관련

| 값 | 지금 | 실제 적용 시 |
|---|---|---|
| `FOOT_POINT_OFFSET_RATIO` | 0.1 | 실제 사람은 검출 박스가 발밑에 더 정확히 맞아 0에 가까울 수 있다. 화면에서 눈으로 확인할 것 |
| `DETECTION_CONFIDENCE_THRESHOLD` | 0.2 | 모형이 작아 낮춰 둔 값. 실제 사람은 훨씬 잘 잡히므로 올릴 수 있다 |
| `DETECTION_IMGSZ` | 320 | 파이 성능에 맞춘 값. 사람이 화면에서 작게 보이면 올려야 한다 |
| `FALL_CONFIG["fall_angle_deg"]` | 20 | 모형의 관절 검출이 부정확해 낮춰 둔 값 |
| `FALL_CONFIG["crosswalk_roi"]` | 화면 비율 | 캘리브레이션을 하면 그쪽이 우선이므로 신경 쓰지 않아도 된다 |

### 프레임률에 묶인 값

`ZONE_RESIDENCY_FRAMES`와 `TRACK_GRACE_FRAMES`는 **프레임 수** 단위라, FPS가 달라지면 실제 시간이 달라진다. 라즈베리파이에서 나오는 실측 FPS를 확인한 뒤 정해야 한다.

```bash
python tools/manual_camera_person_check.py --no-display
```

## 설치 / 실행

Python 3.12 기준. `pedestrian_signal_extension/` 안에서 실행한다.

```bash
uv pip install -r requirements.txt
pytest -q                             # 단위 테스트 (카메라·모델·아두이노 없이 전부 통과)
```

### 처음 한 번: 구역 캘리브레이션

카메라를 **최종 위치에 고정한 뒤** 횡단보도 네 꼭짓점을 순서대로 클릭한다.

```bash
python tools/zone_calibrator.py --width-cm 19 --length-cm 29.2
```

- 클릭 순서: 시작-왼쪽 → 시작-오른쪽 → 끝-오른쪽 → 끝-왼쪽
- `width` = 걷는 방향과 **수직**인 변, `length` = 걷는 방향 변
- **치수를 꼭 넣을 것.** 없으면 속도가 px/s로만 나오고, 구역이 화면 기준으로 나뉘어 실제 거리로는 균등하지 않다
- 카메라를 옮기거나 해상도를 바꾸면 좌표와 호모그래피가 모두 무효가 되어 다시 해야 한다

### 실행

```bash
python main.py                # 전체 (신호 연장 + 쓰러짐 감지)
python main.py --mode fall    # 쓰러짐 감지만 (구역 설정 없이도 동작)
python main.py --no-serial    # 아두이노 없이 판정만 확인
python main.py --display      # 창을 띄운다 (모니터 없으면 쓰지 말 것)
```

### 확인 도구

문제가 생겼을 때 **어디서 끊겼는지** 가르는 용도다. 자동 테스트가 아니라 사람이 눈으로 보는 도구다.

```bash
# 검출·구역·속도·FPS를 한 화면에서 (주력 도구)
python tools/manual_camera_person_check.py --display

# 헤드리스 FPS 실측 (창을 띄우면 렌더링 비용이 섞여 실제보다 낮게 나온다)
python tools/manual_camera_person_check.py --no-display

# 쓰러짐이 왜 안 울리는지 — 각도·키포인트 신뢰도·ROI 겹침을 단계별로 출력
python tools/manual_fall_debug.py --display

# CSI 카메라가 잡히는지만 확인
python tools/manual_rpicam_person_check.py
```

### 라즈베리파이

**라즈베리파이 5 + CSI 리본 카메라.** 파이 5(Bookworm)에는 레거시 카메라 스택이 없어 **CSI 카메라가 `cv2.VideoCapture`로 열리지 않는다.** `CAMERA_SOURCE = "picamera2"`로 두면 Picamera2(libcamera) 경로를 탄다.

```bash
sudo apt install -y python3-picamera2
sudo usermod -aG dialout $USER          # 시리얼 권한 (실행 후 재로그인)
```
