## 2026-08-26: 신호 연장 방식을 세 번 갈아엎었다

하루 만에 프로토콜이 세 번 바뀌었다. 매번 앞 단계에서 발견한 문제가 다음 단계를
불러왔으므로, 그 경위를 남긴다. **최종안이 처음부터 나올 수 있었던 것이 아니라,
앞의 두 안을 만들어 보고 나서야 보인 것들이 있었다.**

### 1차 — 판단을 제어부로 이관 (`EXTEND <초> <ETA|->`)

**계기**: 파이 쪽 `SignalExtensionStateMachine`이 222줄이었다. 잔여 녹색 시간을 시리얼로
읽어 와서 "지금 연장할까"까지 판단하는 구조라, 임계값 비교·누적 상한·엣지 트리거(무장
플래그)가 전부 필요했다.

**깨달은 것**: "남은 시간이 5초 미만인가"는 7세그먼트를 직접 세는 아두이노만 답할 수 있고,
"이 사람이 몇 번 구역에 있나"는 영상을 보는 파이만 답할 수 있다. **각자 자기만 아는 것을
판단하도록 나누면** 파이 쪽 상태 기계가 통째로 사라진다.

**결과**: `signal_extend.py` 222줄 → 130줄. "한 번 상한을 찍으면 영구 CAPPED" 위험
(`bugfix_log.md` B 항목)도 함께 사라졌다 — 누적을 파이가 갖지 않으니 그 버그가 성립하지 않는다.

### 2차 — 한 필드로 (`EXTEND <필요시간>`)

**계기**: 두 필드(`<구역값> <ETA>`)가 아두이노 파싱을 복잡하게 했다. 태그(`EXTEND ETA 7.2` /
`EXTEND ZONE 5`)로 구분하는 안도 검토했으나 채택하지 않았다.

**정한 것**: 숫자 하나로 하되 의미를 **"연장할 초"가 아니라 "앞으로 필요한 시간"**으로
고정했다. 파이는 잔여 시간을 모르므로 뺄셈을 할 수 없고, 뺄셈이 아두이노에서 일어나려면
보내는 값이 '연장량'이 아니라 '필요 시간'이어야 하기 때문이다.

**여기서 사고가 났다**: 의미를 바꾸면서 구역값(3초/5초)을 그대로 뒀더니, 실제 연장이
2·4번 구역에서 **0초**가 됐다. `3 x 1.25 - 5 = -1.25` 라 부족분이 음수였다.
`USE_SPEED_FOR_EXTENSION`이 `False`여서 **항상 그 경로**였는데도 에러가 나지 않아
시뮬레이션을 돌려보고서야 발견했다.

### 3차 — `ZONE <진척도>` (최종)

**계기**: 팀에서 "구역 번호만 보내고 아두이노가 기준표와 비교하자"는 안이 나왔다.
기본 녹색 10초·5구역이면 각 구역 도착 시 9/7/5/3/1초가 남아 있어야 정상이고,
그보다 적으면 뒤처진 것이니 조금씩 연장한다.

**이 방식이 없애준 것**:

| 사라진 것 | 왜 중요했나 |
|---|---|
| ETA 계산과 최소 프레임률(4fps) | 파이 실측이 **3 FPS**였다 — 이전 안에서는 ETA가 아예 안 나올 위험이 있었다 |
| 안전계수 `ETA_SAFETY_MARGIN` | 기준표와의 차이가 곧 부족분이다 |
| **교통약자 검출** | 느린 사람은 기준 대비 지연으로 자동 검출되어 더 연장받는다 |

기준표가 정상 보행 속도를 암묵적으로 담고 있어서 파이가 속도를 잴 필요가 없어졌다.
그리고 매 구역에서 지연을 다시 재는 **피드백 제어**라 오차가 누적되지 않는다 —
저 프레임률로 구역 하나를 건너뛰어도 다음 구역에서 자동으로 만회된다.

**함께 만든 것 — `CrossingProgress`**: 물리 구역 번호는 좌표계 기준이라 진입 방향에 따라
의미가 뒤집힌다. 반대편에서 온 사람의 '2번'은 '거의 다 건넜음'인데 보정 없이는 '대부분
남았음'으로 읽힌다. 방향은 **첫 검출 구역**으로 판별한다(속도가 아니라 위치 이력이라
프레임률 요구가 없다). 중앙에서 처음 보이면 중앙값으로 간주하고 이후 이동으로 확정한다.

**검증**(시뮬레이션): 정상 속도·정시 진입 = 연장 0초 / 5초 늦게 진입 = 6초 /
느린 보행자(구역당 3초) = 4초. 셋 다 건넜다.

## 2026-08-26: 실측으로 확인한 것들

추정으로 적어두면 나중에 근거가 되지 않으므로, 실제로 재서 얻은 값만 남긴다.

### 추론이 프레임 시간의 99.6%다

```
YOLO 추론        :  82.39 ms
쓰러짐 판정+배선  :   0.35 ms      <- 우리 코드 전부
비율             :     237 : 1
```

**이 숫자가 여러 결정의 근거가 됐다.** 우리 코드를 아무리 최적화해도 FPS는 소수점 아래에서만
바뀐다. 반대로 두 파이프라인이 각자 `detect()`를 부르면 FPS가 그대로 반토막 난다 —
`CombinedPipeline`이 추론 결과를 나눠 주는 구조로 만든 이유다.

### `DETECTION_IMGSZ`가 가장 효과적인 튜닝 지점

| imgsz | 추론 시간 | 배수 | 검출 |
|---|---|---|---|
| 640 | 97.4 ms | 1.0× | 4명 |
| 480 | 48.4 ms | 2.0× | 3명 ← 한 명 놓침 |
| **320** | **34.5 ms** | **2.8×** | 4명 |
| 256 | 33.0 ms | 3.0× | 4명 |

320이 가장 좋은 지점이다. **재캘리브레이션이 필요 없다** — YOLO가 내부적으로만 축소하고
박스는 원본 프레임 좌표로 돌아오기 때문이다. `CAMERA_RESOLUTION`을 줄이는 것과 결정적으로
다른 점이고, 그래서 파이가 느릴 때 가장 먼저 건드릴 값이다.

### 서 있는 사람의 몸통 각도는 1~3°

`fall_angle_deg` 기본값 50°와 충분히 분리된다. 정면 사진 기준이므로 사선 구도에서는
다시 재야 하지만, 30°까지 낮출 필요는 없어 보인다.

### ultralytics가 추론 시간을 자동으로 재준다

`results[0].speed` → `{'preprocess': 1.42, 'inference': 49.29, 'postprocess': 1.56}` (ms).
루프 전체 FPS는 카메라 대기·그리기가 섞인 값이라 "무엇이 느린지"를 못 가르는데,
이 값은 추론만 떼어 준다. **첫 호출은 워밍업이라 2배 느리므로 측정에서 제외할 것.**

## 2026-08-26: 경로가 실행 디렉터리에 종속돼 있었다

같은 원인의 문제가 세 곳에서 나왔고, 셋 다 **에러 메시지가 경로를 탓하지 않아** 찾기 어려웠다.

1. **`ZONE_CONFIG_PATH`가 상대 경로** — `tools/`에서 캘리브레이터를 돌리면 `tools/data/`가
   생기고, 프로젝트 루트에서 `main.py`를 돌리면 그걸 못 찾는다.
2. **절대 경로로 바꾼 뒤 앞 슬래시 사고** — `Path(root) / "/data"` 는 pathlib이 앞 경로를
   통째로 버려서 `C:\data`(파이에서는 `/data`, 파일시스템 최상위)를 가리킨다. 파이에서는
   권한 오류로 저장 자체가 실패한다.
3. **모델 가중치도 같은 문제** — 리포 루트에서 실행하면 `yolov8n-pose.pt`를 못 찾아
   6.5MB를 다시 내려받고 실행 위치마다 사본이 생겼다. 파인튜닝 가중치는 내려받을 곳도 없어
   그냥 실패한다.

**대응**: 셋 다 프로젝트 루트 기준 절대 경로로 바꾸고, `tests/test_config_paths.py`로 고정했다.
가중치는 "있으면 절대 경로, 없으면 이름 그대로"라 최초 클론 시 자동 다운로드는 살아 있다.

## 2026-08-25: 한 프레임만 놓쳐도 누적이 리셋됐다

**증상**: 검출이 한 프레임이라도 끊기면 그 사람의 잔류 카운트가 0으로 돌아가고 속도
히스토리가 통째로 지워졌다. YOLO는 가림·모션블러·저조도에서 한두 프레임씩 놓치는 것이
정상인데, 그때마다 확정 보행자 자격을 잃었다.

**왜 위험한가**: 에러가 나지 않는다. 현장에서는 "왜 가끔 연장이 안 되지"로만 보인다.

**대응**: `TRACK_GRACE_FRAMES = 2` 도입. 유예 동안 카운트는 **동결**한다 — 안 보이는 동안은
잔류의 증거가 없으므로 올려주지 않되, 이미 쌓은 것을 뺏지도 않는다.
단 **'구역 밖으로 나감'은 유예 대상이 아니다**(즉시 리셋). "안 보임"은 정보가 없는 상태지만
"밖으로 나감"은 확실한 정보라, 둘을 같이 취급하면 이미 떠난 사람 때문에 차를 세우게 된다.

**단위를 '초'가 아니라 '프레임 수'로 한 이유**: 잔류 확정 자체가 프레임 수 기준이라 같은
단위여야 섞이지 않는다. `FALL_CONFIG`의 `track_grace_sec`이 '초 + 프레임 배수' 적응형인
것은 그쪽 누적(`fall_confirm_sec`)이 시간 기준이라서다.

## 2026-08-25: 시리얼 통신과 쓰러짐 → 부저 배선

**한 보드가 부저·LED·7세그먼트를 다 담당**하기로 해서 시리얼 채널도 하나로 갔다.
프레이밍은 개행으로 끝나는 ASCII 한 줄로 확정.

**수신을 `poll()` 한 곳으로 모은 이유**: 한 채널로 여러 종류의 줄이 섞여 온다.
"필요할 때 `readline()` 한 번" 방식이면 명령이 늘어날 때 서로의 응답을 잡아먹는다
(잔여 시간을 읽으려다 `OK ALERT`를 먹어버리는 식).

**전송 정책 — 변화 시 + 1초 하트비트**:
- 매 프레임 보내면 아두이노의 64바이트 수신 버퍼가 넘치고, 응답까지 하면
  그 송신 시간(13바이트당 13.5ms)에 아두이노 루프가 묶인다
- 변화 시에만 보내면 그 한 줄을 놓쳤을 때 아두이노가 **영영 옛 상태로 남는다**
- 하트비트가 있어야 아두이노가 "N초간 조용함 = 파이가 죽음"을 워치독으로 쓸 수 있다

**`--mode fall` 신설**: 쓰러짐 감지는 제어부 프로토콜에 의존하지 않으므로 먼저 완결할 수
있었다. 카메라 → YOLO → 쓰러짐 판정 → 부저까지 한 줄로 돈다.

## 축척 분석 — 모형 치수를 정하면서

모형 횡단보도가 폭 10cm × 길이 30cm면 실제 4차선 횡단보도(400cm × 1200cm)의 **1:40 축소판**이다.

중요한 것은 거리 축척이 아니라 **시간 축척**이다. 연장 시간은 거리가 아니라 시간이고,
`시간 축척 = 거리 축척 / 속도 축척` 이므로 모형 보행자를 **2.5 cm/s**(실제 보행속도의 1/40)로
움직이면 시간 축척이 1:1이 되어 국내 운영 사례의 초 단위 값을 그대로 쓸 수 있다.

    검산: 30cm / 2.5cm/s = 12초  ==  실제 12m / 1.0m/s = 12초

**모터 속도를 맞추는 것이 연장 초를 바꾸는 것보다 낫다.** 값을 임의로 축소하면 근거 자료
(광주시 5초, 서울시 3~6초, 강진군 5~10초)와의 연결이 끊어진다.

## 배운 것 (회고)

**① 조용히 틀리는 버그가 가장 비쌌다.** 이번에 찾은 것들이 거의 다 그랬다 — 경로 종속,
config 체인 대입(`PRIORITY_ZONE_EXTENSION_SEC = ZONE_EXTENSION_SEC = {...}` 때문에 일반
보행자에게도 교통약자 값이 나가고 있었다), 의미 변경 후 남은 옛 값. 전부 에러가 안 나서
시뮬레이션이나 테스트를 돌려보고서야 보였다.

**② 값을 바꾸면 그 값의 '의미'도 확인해야 한다.** 2차 개편에서 `EXTEND` 뒤 숫자의 의미를
'연장량'에서 '필요 시간'으로 바꿨는데, 구역값 3초/5초는 그대로 뒀다. 단위가 섞여
연장이 0초가 됐다. **의미를 바꾼 뒤에는 그 자리에 있던 값이 여전히 유효한지 다시 봐야 한다.**

**③ 테스트가 자기 값을 소유해야 한다.** `config`를 읽는 테스트는 config를 만질 때마다
깨진다. 실제로 그렇게 깨진 덕분에 체인 대입 버그를 찾긴 했지만, 그건 운이었다.

**④ 실측이 설계를 바꿨다.** 파이 3 FPS라는 숫자가 없었다면 ETA 기반 설계를 그대로 갔을
것이고, 현장에서 "속도가 왜 안 나오지"를 겪었을 것이다.
