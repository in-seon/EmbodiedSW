## 왜 한 번에 크게 주지 않고 조금씩 나누는가

크게 한 번 주면 보행자가 곧바로 건너가도 되돌릴 수 없다. **낭비의 상한이 곧 1회 연장량**이다.

나눠 주면 매 구역에서 지연을 다시 재는 **피드백 루프**가 되어, 뛰어가는 사람은 다음 구역에서 지연이 줄어 연장도 자연히 줄어든다.

다만 1회 연장량을 하트비트 주기(1초)와 같게 두면 안 된다. 매 하트비트마다 연장이 붙어 7세그먼트가 깜빡이는 것처럼 보인다.

## 보행 속도 기준 — 국내 산정 기준

국내 보행신호시간은 **"보행진입시간 7초 + 횡단보도 1m당 1초"**(보행속도 1.0 m/s)로 산정하고, 교통약자가 많은 지역은 **"0.8m당 1초"**(0.8 m/s)로 완화한다. 그 비율이 `1.0 / 0.8 = 1.25`다.

노인의 15th percentile 보행속도가 **0.85 m/s**로 측정된 연구가 있어, 기준 속도보다 느린 보행자가 실재한다는 것이 확인된다.

**위험이 비대칭이라는 점이 중요하다.** 과대 연장은 차량이 조금 더 기다리는 것이지만, 과소 연장은 **보행자가 도로에 갇히는 것**이다. 애매하면 더 주는 쪽으로 설계했다.

## 축척 — 모형에서 실제 초 단위 값을 그대로 쓰려면

거리만 줄이면 시간이 맞지 않는다.

```
시간 축척 = 거리 축척 ÷ 속도 축척
```

모형 보행자를 **실제 보행 속도와 같은 비율로** 느리게 움직이면 시간 축척이 1:1이 되어, 위의 운영 사례 값을 그대로 쓸 수 있다.

예를 들어 실제 4차선 횡단보도(폭 400cm × 길이 1200cm)의 1:40 축소판이라면, 모형 보행자를 실제 1.0 m/s의 1/40인 **2.5 cm/s**로 움직인다.

```
검산: 30cm ÷ 2.5cm/s = 12초  ==  실제 12m ÷ 1.0m/s = 12초
```

**모터 속도를 맞추는 것이 연장 초를 바꾸는 것보다 낫다.** 초를 임의로 축소하면 위 근거 자료와의 연결이 끊어진다. 모터가 더 빠를 수밖에 없다면 시간 축척만큼 초를 나누되, **비율은 유지**하는 편이 설명하기 좋다.

## 구역 5등분을 실거리로 하는 이유 — 측정값

폭 400cm × 길이 1000cm 횡단보도를 사선으로 본 좌표 `[(80,460), (560,460), (400,150), (240,150)]`로 측정했다.

| 분할 방식 | 1번 | 2번 | 3번 | 4번 | 5번 |
|---|---|---|---|---|---|
| 화면(픽셀) 기준 | 77cm | 105cm | 152cm | 238cm | 429cm |
| 실거리(cm) 기준 | 200cm | 200cm | 200cm | 200cm | 200cm |

화면 기준으로는 1번과 5번이 **5.6배** 차이났고, **횡단보도의 실제 한가운데(500cm)가 3번이 아니라 4번 구역**에 들어갔다. "정중앙일수록 더 연장한다"는 전제 자체가 무너지는 값이다.

사영변환은 직선을 직선으로 보내므로, 평면상 직사각형 띠의 네 꼭짓점만 역변환하면 화면상 정확한 구역 사각형이 된다(근사가 아니다).

# 2. 실측 기록

추정으로 적어두면 나중에 근거가 되지 않으므로, 실제로 재서 얻은 값만 남긴다.

## 추론이 프레임 시간의 99.6%다

```
YOLO 추론        :  82.39 ms
우리 코드 전부    :   0.35 ms
비율             :     237 : 1
```

**이 숫자가 여러 결정의 근거가 됐다.** 우리 코드를 아무리 최적화해도 FPS는 소수점 아래에서만 바뀐다. 반대로 두 판정이 각자 `detect()`를 부르면 FPS가 그대로 반토막 난다 — 추론 결과를 나눠 주는 구조로 만든 이유다.

## `DETECTION_IMGSZ`가 가장 효과적인 튜닝 지점

| imgsz | 추론 시간 | 배수 | 검출 |
|---|---|---|---|
| 640 | 97.4 ms | 1.0× | 4명 |
| 480 | 48.4 ms | 2.0× | 3명 ← 한 명 놓침 |
| **320** | **34.5 ms** | **2.8×** | 4명 |
| 256 | 33.0 ms | 3.0× | 4명 |

**재캘리브레이션이 필요 없다** — YOLO가 내부적으로만 축소하고 박스는 원본 프레임 좌표로 돌아온다. `CAMERA_RESOLUTION`을 줄이는 것과 결정적으로 다른 점이고, 그래서 파이가 느릴 때 가장 먼저 건드릴 값이다.

## 라즈베리파이 실측 FPS

디스플레이를 켠 상태에서 **약 8 FPS**. 창을 띄우면 렌더링·전송 비용이 섞이므로 `--no-display`로 다시 재는 것이 정확하다.

이 숫자가 설계를 바꿨다 — 아래 "세 번 갈아엎었다" 항목 참고.

## 사람 검출

COCO 사전학습 `yolov8n`이 사람 모형을 `person`으로 검출했고 신뢰도가 **80%대**였다. 추가 파인튜닝이 필요 없다고 판단했다.

포즈 모델로 바꾼 뒤 4명이 있는 이미지에서:

```
PersonDetector.detect() -> 4명, 120 ms
  id=1 conf=0.89 keypoints=(17,3) 몸통각도=1.1
  id=2 conf=0.88 keypoints=(17,3) 몸통각도=1.7
  id=3 conf=0.85 keypoints=(17,3) 몸통각도=None   <- 키포인트 신뢰도 낮음 -> 비율 폴백
  id=4 conf=0.61 keypoints=(17,3) 몸통각도=None
```

**서 있는 사람의 몸통 각도는 1~3°** 로 나온다. 쓰러짐 임계값과 충분히 분리된다. 다만 정면 사진 기준이므로 사선 구도에서는 다시 재야 한다.

## 추론 시간만 따로 재는 법

`results[0].speed` → `{'preprocess': 1.42, 'inference': 49.29, 'postprocess': 1.56}` (ms).

루프 전체 FPS는 카메라 대기·그리기가 섞인 값이라 "무엇이 느린지"를 못 가른다. **첫 호출은 워밍업이라 2배 느리므로 측정에서 제외할 것.**

# 3. 설계가 바뀐 과정

## 초기 결정 (2026-08-05)

- **검출 모델**: COCO 사전학습 `yolov8n`. 사람 모형이 80%대로 검출돼 파인튜닝 불필요.
- **카메라 경로**: 라즈베리파이 5 + CSI 리본 카메라로 확정. 파이 5는 Bookworm 이상만 지원하고 Bookworm에는 레거시 카메라 스택(`bcm2835-v4l2`)이 없어 **CSI 카메라가 `/dev/video0`으로 잡히지 않는다.** `cv2.VideoCapture(0)`은 실패한다 → Picamera2 백엔드 추가.
  > Picamera2의 `format="RGB888"`은 이름과 달리 메모리상 **BGR 순서** 배열을 반환한다(libcamera 명명 규칙). 덕분에 cv2 경로와 형식이 일치해 하위 단계가 카메라 종류를 몰라도 된다.
- **구역 5등분을 실거리 기준으로** (위 측정값 참고).

## 포즈 모델로 교체 (2026-08-19)

목표 1(신호 연장)은 사람 박스가, 목표 2(쓰러짐 감지)는 몸통 각도를 재기 위한 키포인트가 필요하다. **모델을 따로 두면 추론이 2배가 되는데, 추론이 프레임 시간의 사실상 전부다.**

포즈 모델 하나가 박스와 키포인트를 동시에 주므로 `yolov8n-pose.pt`로 교체했다.

**신뢰도 임계값은 낮은 쪽을 택했다.** 넘어지는 순간 bbox가 급변하고 신뢰도가 떨어져 검출이 통째로 빠지는 구간이 생기는데(UR Fall 실측에서 확인), **쓰러진 사람을 놓치는 것이 연장 오탐보다 훨씬 위험하다.**

> 되돌리는 법: `DETECTION_MODEL_PATH`를 `yolov8n.pt`로 되돌리면 신호 연장은 그대로 동작하고, 쓰러짐 감지는 키포인트 없이 bbox 가로/세로 비율 폴백으로 동작한다. 코드 수정 없이 config 한 줄이다.

## 신호 연장 방식을 세 번 갈아엎었다 (2026-08-26)

하루 만에 프로토콜이 세 번 바뀌었다. **최종안이 처음부터 나올 수 있었던 것이 아니라, 앞의 두 안을 만들어 보고 나서야 보인 것들이 있었다.**

### 이전 구조 — 파이가 다 판단했다

파이가 잔여 녹색 시간을 시리얼로 **읽어 와서** "지금 연장할까"까지 판단했다. 자기가 소유하지 않은 값으로 상태를 추론해야 해서 임계값 비교·누적 상한·엣지 트리거(무장 플래그)가 전부 필요했고, `signal_extend.py`가 222줄이었다.

### 1차 — 판단을 아두이노로 이관

**깨달은 것**: "남은 시간이 5초 미만인가"는 7세그먼트를 직접 세는 아두이노만 답할 수 있고, "이 사람이 몇 번 구역에 있나"는 영상을 보는 파이만 답할 수 있다. **각자 자기만 아는 것을 판단하도록 나누면** 파이 쪽 상태 기계가 통째로 사라진다.

**결과**: 222줄 → 130줄. "한 번 상한을 찍으면 영구히 연장 불가" 위험도 함께 사라졌다 — 누적을 파이가 갖지 않으니 그 버그가 성립하지 않는다.

### 2차 — 한 필드로

두 필드(`<구역값> <ETA>`)가 아두이노 파싱을 복잡하게 했다. 숫자 하나로 하되 의미를 **"연장할 초"가 아니라 "앞으로 필요한 시간"**으로 고정했다. 파이는 잔여 시간을 모르므로 뺄셈을 할 수 없고, 뺄셈이 아두이노에서 일어나려면 보내는 값이 '연장량'이 아니라 '필요 시간'이어야 하기 때문이다.

**여기서 사고가 났다.** 의미를 바꾸면서 구역값(3초/5초)을 그대로 뒀더니 2·4번 구역에서 실제 연장이 **0초**가 됐다(`3 × 1.25 − 5 = −1.25`, 부족분이 음수). 그 경로가 기본값이었는데도 에러가 나지 않아 시뮬레이션을 돌려보고서야 발견했다.

### 3차 — `zone<진척도>` (최종)

팀에서 "구역 번호만 보내고 아두이노가 기준표와 비교하자"는 안이 나왔다.

```
기준[n] = 기본녹색 × (1 - (2n-1)/(2N))     # 10초/5구역 -> 9,7,5,3,1
```

"정상 속도로 걸었다면 n번째 구역에 도착했을 때 이만큼 남아 있어야 한다"이므로, 실제 잔여시간과의 차이가 곧 그 사람의 지연이다.

**이 방식이 없애준 것**

| 사라진 것 | 왜 중요했나 |
|---|---|
| ETA 계산과 최소 프레임률(4fps) 요구 | 파이 실측이 낮았다 — 이전 안에서는 ETA가 아예 안 나올 위험이 있었다 |
| 안전계수 | 기준표와의 차이가 곧 부족분이다 |
| **교통약자 검출** | 느린 사람은 기준 대비 지연으로 자동 검출되어 더 연장받는다 |

**최솟값 하나만 보내면 되는 것도 수학적으로 보장된다.** 기준표가 진척도에 대해 단조 감소하고 모든 사람이 같은 잔여시간을 보므로, `부족분 = 기준[n] − 잔여`는 진척도가 작을수록 항상 크다.

**함께 만든 것 — 진척도 보정**: 물리 구역 번호는 좌표계 기준이라 진입 방향에 따라 의미가 뒤집힌다. 반대편에서 온 사람의 '2번'은 '거의 다 건넜음'인데 보정 없이는 '대부분 남았음'으로 읽혀 엉뚱한 사람이 최솟값을 차지한다.

방향은 **첫 검출 구역**으로 판별한다(속도가 아니라 위치 이력이라 프레임률 요구가 없고, 사람이 멈춰 있어도 유지된다). 중앙에서 처음 보이면 중앙값으로 간주하고 이후 이동으로 확정한다. 3→4든 3→2든 진척도 4로 수렴한다.

오판하면 진척도가 **실제보다 작게** 나오고, 작은 진척도는 '덜 왔다'이므로 **더 연장하는** 쪽으로 틀린다 — 안전한 방향의 오차다.

**검증**(시뮬레이션): 정상 속도·정시 진입 = 연장 0초 / 5초 늦게 진입 = 6초 / 느린 보행자 = 4초. 셋 다 건넜다.

## 모형 구동 모터와 서보 (2026-08-27 → 08-29에 이관)

모형 보행자를 움직이는 스텝모터와 발에 붙여 넘어뜨리는 서보를 파이 GPIO에 붙였다가, **별도 보드가 맡기로 하면서 파이 쪽 코드를 전부 제거했다.** 시리얼도 다시 한 방향이 됐다.

코드는 지웠지만 **하드웨어와 무관한 교훈은 남는다.** 구동을 맡는 보드에서 그대로 겪을 것들이다.

**① 정지 조건은 '없음'이 아니라 '있었다가 없어짐'이어야 한다.**

```
녹색 시작 -> 모형은 아직 횡단보도 밖 -> 확정 보행자 0명 -> "나갔다" -> 즉시 정지
```

가장 자연스러운 구현이 틀렸다. 녹색이 막 켜진 시점엔 모형이 아직 진입 전이라 0명이다. "본 적이 있다"는 래치가 필요하고, **그 래치를 다음 사이클에 비우지 않으면 첫 횡단만 되고 두 번째부터 안 된다.**

**② 물리 장치에는 안전 타임아웃이 필요하다.** 정지 조건이 영영 오지 않으면 소프트웨어는 로그 한 줄로 끝나지만 모터는 탄다.

**③ 넘어진 모형을 계속 끌고 가면 안 되고, 그 멈춤은 '정지'가 아니라 '일시정지'다.**

| | 뜻 | 래치 | 재개 |
|---|---|---|---|
| 정지 | 이번 횡단이 끝났다 | 지운다 | 다음 시작 신호 |
| 일시정지 | 같은 횡단 도중 잠깐 | **유지한다** | 재개 신호 |

정지로 처리하면 일어난 뒤의 이동이 새 사이클로 오해되고, 그 시점엔 이미 확정 보행자가 있으므로 **곧바로 '횡단 완료'로 판정돼 영영 안 움직인다.**

파생 함정: **누우면 검출이 빠진다**(bbox 모양이 급변해 트래커가 ID를 새로 달거나 놓침). 일시정지 중에는 정지 판단 자체를 건너뛰어야 한다. 그리고 연출로 세워 둔 시간은 안전 타임아웃에서 빼야 한다.

**④ 스텝 루프는 별도 스레드여야 한다.** 스텝 간격 5ms vs 비전 루프 100~330ms — **두 자릿수 차이라 같은 스레드에 둘 수 없다.** 한 프레임에 한 스텝이면 모터가 20배 느려진다. 반대로 서보는 각도만 지정하면 하드웨어 PWM이 유지하므로 스레드가 필요 없다.

> 구현과 테스트는 커밋 `ab4064e` / `8d28903`에 남아 있다.

## 교통약자 별도 검출 제거 (2026-08-30)

별도 가중치로 휠체어·목발을 잡는 검출기와 관련 설정을 전부 지웠다.

**왜 필요 없어졌나** — 구역 기준표가 정상 보행 속도를 담고 있어서다. 느린 사람은 기준 대비 지연으로 자동 검출되어 더 연장받는다. **"휠체어인가"를 알 필요 없이 "느린가"만 보면 되고, 그건 이 방식이 이미 잰다.** 애초에 공개 휠체어 데이터셋은 실제 사람·휠체어 사진으로 학습돼 있어 축소 모형은 못 잡을 가능성이 높았다.

**왜 남겨 두지 않았나** — 8월 26일에는 "계측용으로 남긴다"고 했다. 그런데 남은 `MOBILITY_AID_MODEL_PATH = None`, `MOBILITY_AID_LABELS = (...TODO...)` 가 문서에서 계속 **"아직 채워야 할 값"**처럼 보였다. 쓰이지 않는 설정이 미결 항목 목록에 남아 있으면 볼 때마다 "이걸 해야 하나"를 다시 판단하게 된다. 그 비용이 계측 가치보다 컸다.

`src/speed.py`는 그대로 뒀다 — 화면에 실제로 표시되고 발표 자료에 쓸 수 있는 값이라, 같은 기준(쓰이는가)으로 봐도 남길 이유가 있다.

## track_id 재발급 상속 (2026-08-30)

추적기가 같은 사람에게 새 ID를 주면 잔류 카운트가 0으로 돌아갈 뿐 아니라 **진입 방향이 통째로 날아간다.** 시뮬레이션으로 확인한 결과:

```
정상 추적 (id 유지):   물리구역 1 2 3 4 5 → 진척도 1 2 3 4 5
4번에서 ID 재발급:     물리구역   4 5     → 진척도   2 1   ← 방향이 뒤집힘
```

거의 다 건넌 사람이 "방금 진입"으로 보고되고, **진척도가 감소하면서 아두이노가 매번 새로 연장한다.** 재확정 지연(0.25초)보다 이쪽이 훨씬 비싸다.

쓰러짐 감지에는 이미 같은 보정이 있었다(bbox 겹침 기준). 신호 연장 쪽은 발 위치만 받으므로 **거리**로 맞췄다 — 구역 판정과 같은 좌표다.

**남는 한계**: 두 사람이 반대 방향으로 교차하면서 동시에 ID를 잃으면 서로 뒤바뀔 수 있다. 교차 지점에서는 두 사람의 위치가 사실상 같으므로 위치 기반으로는 원리적으로 구분이 안 된다. 틀리는 방향은 안전한 쪽(더 연장)이고 누적 상한이 막는다.

**임계값은 위아래가 모두 막혀 있다.**

- 하한 — 공백 동안 사람이 움직인 거리보다 커야 한다. 아니면 상속이 아예 안 된다.
- 상한 — **구역 하나의 길이를 넘으면 안 된다.** 넘으면 옆 구역의 다른 사람을 잇는다.

## 발 위치 기준점 보정 (2026-08-30)

모형이 살짝 떠 보여서 판정 기준점을 박스 하단에서 높이의 10%만큼 올렸다.

**픽셀이 아니라 비율로 한 것이 핵심이다.** 고정 픽셀값을 쓰면 멀리 있는 사람(박스가 작음)은 과보정되고 가까운 사람은 과소보정된다.

같은 공식이 두 곳에 복사돼 있어서 한쪽만 고치면 조용히 어긋날 뻔했다 — 함께 정리했다.

# 4. 겪은 버그

## 실시간 루프와 모듈의 이음매 (2026-08-19)

하드웨어가 없어 실행 검증을 못 하는 상태에서 코드 리뷰로 4건을 찾았다. **네 건 모두 각 모듈은 정상인데 모듈이 맞물리는 이음매에서 생긴 문제**다. 기존 테스트 83개가 전부 통과하고 있었는데도 잡히지 않은 이유가 이것이다 — 각 모듈을 단독으로는 검증했지만, **"실시간 루프가 매 프레임 호출한다"는 사실을 반영한 테스트가 없었다.**

**A. 상태 머신이 프레임마다 연장을 누적했다.** 10fps에서 프레임별 발급값이 `[5, 5, 5, 0, 0, ...]` — **0.3초 만에 사이클 예산을 전부 소진**하고 제어부로 명령이 3연타로 나갔다. "매 사이클 재평가"라는 설계 의도가 프레임 루프에 물리면서 "매 프레임 재연장"이 돼 있었다.

**B. 사이클 리셋 함수를 아무도 호출하지 않았다.** 첫 사이클에서 상한에 도달하면 **그 뒤 모든 사이클에서 영구히 연장 불가**가 된다. A와 결합하면 특히 나쁘다 — 0.3초 만에 상한을 찍고 그 상태가 영구히 유지된다. **시연 중 첫 번째 보행자 이후로 시스템 전체가 조용히 죽는다.** 예외도 로그도 없이.

> A와 B는 연장 판단을 아두이노로 이관하면서 **문제 자체가 사라졌다.** 누적을 파이가 갖지 않으면 성립하지 않는 버그다.

**C. 캘리브레이션 해상도를 저장만 하고 검증하지 않았다.** 캘리브레이션 당시 해상도와 운영 해상도가 다르면 **에러 없이 구역만 엉뚱하게 잡힌다.** zone 좌표와 호모그래피는 둘 다 당시 해상도에 종속된 픽셀 값이다. 해상도를 낮추는 순간 바로 이 상황이 된다 → 불일치 시 즉시 실패하도록 검증을 넣었다.

**D. `track_id=None`을 두 소비자가 다르게 다뤘다.** 속도 추정은 무시하는데 잔류 추적은 `None`을 그대로 키로 썼다. 한 프레임에 ID 없는 3명이 들어오면 같은 카운터를 각각 증가시켜 **즉시 확정**됐다. 검출 흔들림을 걸러내려고 둔 장치가 **정확히 추적이 불안정한 순간에** 무력화된다 — 방어 장치로서 최악의 실패 방식이다.

> 다만 **조용히 버리지 않는다.** 무시한 개수를 노출해 "추적이 자주 끊기고 있다"는 사실이 보이게 했다.

## 한 프레임만 놓쳐도 누적이 리셋됐다 (2026-08-25)

YOLO는 가림·모션블러·저조도에서 한두 프레임씩 놓치는 것이 정상인데, 그때마다 확정 보행자 자격을 잃었다. **에러가 나지 않는다.** 현장에서는 "왜 가끔 연장이 안 되지"로만 보인다.

유예를 도입하되 **카운트는 동결**한다 — 안 보이는 동안은 잔류의 증거가 없으므로 올려주지 않되, 이미 쌓은 것을 뺏지도 않는다.

단 **'구역 밖으로 나감'은 유예 대상이 아니다**(즉시 리셋). "안 보임"은 정보가 없는 상태지만 "밖으로 나감"은 확실한 정보라, 둘을 같이 취급하면 이미 떠난 사람 때문에 차를 세우게 된다.

**단위를 '초'가 아니라 '프레임 수'로 한 이유**: 잔류 확정 자체가 프레임 수 기준이라 같은 단위여야 섞이지 않는다. 쓰러짐 쪽이 '초 + 프레임 배수' 적응형인 것은 그쪽 누적이 시간 기준이라서다.

## 경로가 실행 디렉터리에 종속돼 있었다 (2026-08-26)

같은 원인의 문제가 세 곳에서 나왔고, 셋 다 **에러 메시지가 경로를 탓하지 않아** 찾기 어려웠다.

1. **구역 설정 경로가 상대 경로** — `tools/`에서 캘리브레이터를 돌리면 `tools/data/`가 생기고, 루트에서 `main.py`를 돌리면 그걸 못 찾는다.
2. **절대 경로로 바꾼 뒤 앞 슬래시 사고** — `Path(root) / "/data"` 는 pathlib이 앞 경로를 통째로 버려서 파일시스템 최상위를 가리킨다. 파이에서는 권한 오류로 저장 자체가 실패한다.
3. **모델 가중치도 같은 문제** — 리포 루트에서 실행하면 가중치를 못 찾아 6.5MB를 다시 내려받고 실행 위치마다 사본이 생겼다.

셋 다 프로젝트 루트 기준 절대 경로로 바꾸고 테스트로 고정했다.

## 정지한 사람의 ETA 폭주

`crossing_speed <= 0`만 걸러서, 서 있는 사람의 부동소수점 오차가 거대한 ETA로 증폭됐다. 실측 관측값이 **`ETA=10351225.3s`**. 파이 안에서만 쓸 때는 구역값이 상한이라 무해했지만, 그 값을 밖으로 내보내는 순간 문제가 된다 → 최소 속도 임계값을 뒀다.

## 시리얼 수신을 한 곳으로 모은 이유

한 채널로 여러 종류의 줄이 섞여 온다. "필요할 때 `readline()` 한 번" 방식이면 명령이 늘어날 때 **서로의 응답을 잡아먹는다**(잔여 시간을 읽으려다 다른 응답을 먹어버리는 식).

## 정해야 할 것

- [ ] **`fall` 수신 시 신호를 어떻게 할 것인가.** 부저만? 차량 신호 적색 유지? 쓰러진 사람은 스스로 못 건너므로 연장으로 해결되는 상황이 아니고, 무한 연장은 교차 방향 차량을 막아 2차 사고를 부른다.
- [ ] **보드레이트를 파이 config와 맞출 것.** 스케치의 `Serial.begin()` 값과 다르면 연결 자체가 실패한다.
- [ ] **무신호 워치독.** 2~3초간 아무 메시지도 안 오면 파이가 죽었거나 USB가 빠진 것이다. `normal`로 되돌리고 부저를 끈다. 파이 하트비트가 1초라 정상 동작 중에는 발동하지 않는다.

## 판정 시점 — 검토가 필요한 부분

원래 계약은 "**구역이 바뀐 순간에만** 판정"이었다. 파이가 같은 값을 1초마다 재전송하므로 받을 때마다 판정하면 같은 구역에서 계속 연장된다는 우려에서였다.

그런데 시뮬레이션 결과 **그 규칙이 느린 보행자에게 불리하다.**

| 상황 | 구역만 판정 | 구역+잔여시간 판정 |
|---|---|---|
| 정상 보행자 | 2s → 통과 | 2s → 통과 |
| 아주 느린 보행자 | **2s** → 못 건넘 | **10s** → 못 건넘 |
| 중간에 멈춤 | **0s → 못 건넘** | **8s → 통과** |

**판정 횟수가 걷는 속도에 묶여 있다.** 느리게 걸을수록 구역 경계를 적게 지나므로 판정 기회가 적어진다 — 도움이 가장 필요한 사람이 판정을 가장 적게 받는다. 멈춰 선 사람은 0번이다.

매초 판정해도 무한 증식하지 않는다. 조건에 가드가 있기 때문이다:

```c
if (greenRemaining < base(zone)) { greenRemaining += 연장량; }
```

연장할 때마다 잔여가 올라가고 기준에 도달하면 조건이 거짓이 되어 **스스로 멈춘다.** 평형점이 있고, 누적 상한이 사이클 전체를 다시 묶는다.

> 단, **가드 없이 조건 없이 더하면 진짜 버그다.** 매초 붙어서 상한까지 즉시 소진되고 연장이 사실상 "무조건 최대"가 된다.

## 알고 있어야 할 한계

- **서 있기만 하는 사람도 연장을 소진한다.** 잔류 확정은 "계속 보인다"까지만 보고 "건너는 중인가"는 구분하지 않는다. 누적 상한이 막지만, 시연에서 모형을 세워둔 채 두면 그렇게 동작한다.
- **늦게 진입한 사람에게 관대하다.** 시간이 얼마 안 남았을 때 들어와도 기준 대비 지연으로 잡혀 연장을 받는다. 상한이 총량을 막고, 뛰어가면 다음 구역에서 지연이 줄어 자연히 멎는다.
- **연속 진입은 값이 안 바뀔 수 있다.** 한 사람이 진척도 1에 있는 동안 다른 사람이 또 진입하면 최솟값이 그대로 1이라 아두이노가 변화를 못 본다. 다만 시뮬레이션상 **총 연장량에는 차이가 없었다** — 최소 진척도인 사람이 곧 마지막 진입자이고, 그 사람이 구역을 지나가면서 판정을 계속 일으키기 때문이다.

# 6. 남은 실측 / 미결

| 항목 | 상태 |
|---|---|
| 라즈베리파이 헤드리스 실측 FPS | `--no-display`로 측정 필요. 프레임 수 기준 값들의 근거가 된다 |
| 발 위치 기준점 비율 | 화면에서 빨간 점이 실제 접지점에 오는지 보고 조정 |
| track_id 상속 거리 | 발 위치 지터를 실측한 뒤 조정. 구역 크기보다 작아야 한다 |
| 쓰러짐 임계값 | 사선 구도에서 다시 재야 한다. 정면 사진 기준값과 다르다 |
| 아두이노 스케치 | 하드웨어 담당 |
| 텔레그램 신고 | 봇 토큰 보관 방식 + 범위 미결정 |

**미확정 값이 있는 상태로 관련 모듈을 실행하면 `NotImplementedError`가 나도록 만들어, 값을 임의로 추정해 쓰지 않게 했다.** 조용히 틀린 값으로 도는 것보다 멈추는 편이 낫기 때문이다.

# 7. 배운 것

**① 조용히 틀리는 버그가 가장 비쌌다.** 찾은 것들이 거의 다 그랬다 — 경로 종속, config 체인 대입(`PRIORITY_ZONE_EXTENSION_SEC = ZONE_EXTENSION_SEC = {...}` 때문에 일반 보행자에게도 교통약자 값이 나가고 있었다), 의미 변경 후 남은 옛 값. 전부 에러가 안 나서 시뮬레이션이나 테스트를 돌려보고서야 보였다.

**② 값을 바꾸면 그 값의 '의미'도 확인해야 한다.** 2차 개편에서 숫자의 의미를 '연장량'에서 '필요 시간'으로 바꿨는데 구역값은 그대로 뒀다. 단위가 섞여 연장이 0초가 됐다. **의미를 바꾼 뒤에는 그 자리에 있던 값이 여전히 유효한지 다시 봐야 한다.**

**③ 테스트가 자기 값을 소유해야 한다.** config를 읽는 테스트는 config를 만질 때마다 깨진다. 실제로 네 번 깨졌다. 마지막은 유예 프레임 수를 2에서 5로 올렸을 때였는데, **코드는 정상이고 테스트 가정이 낡은 것**이었다.

**④ 통과하는 테스트가 잘못된 동작을 지켜주고 있을 수 있다.** 상한 검증 테스트가 **버그 동작을 그대로 인코딩**하고 있었다(연속 두 번 호출로 상한 도달). 테스트가 통과한다고 동작이 옳은 것은 아니다.

**⑤ 실측이 설계를 바꿨다.** 파이 FPS라는 숫자가 없었다면 ETA 기반 설계를 그대로 갔을 것이고, 현장에서 "속도가 왜 안 나오지"를 겪었을 것이다.

**⑥ "각자 자기만 아는 것을 판단한다"가 계속 답이었다.** 연장 프로토콜 3회 개편, 부저 끄는 시점, 모터 기동/정지까지 전부 같은 원칙 한 줄로 갈렸다. 판단을 **정보를 가진 쪽**에 두면 주고받는 메시지가 저절로 줄어든다.

**⑦ 부품이 각자 맞는 것과 함께 있을 때 맞는 것은 다르다.** 모터 두 개를 각각 올바르게 만들어 놓고, 둘이 동시에 도는 장면을 상상하지 않았다. 넘어진 모형이 끌려가는 그림은 코드를 아무리 봐도 안 보이고 **데모를 머릿속에서 재생해야** 보인다.

**⑧ 물리 장치는 조용한 실패가 없다 — 대신 타는 실패가 있다.** 소프트웨어라면 "정지 조건이 안 와서 루프가 계속 도는" 버그가 로그 한 줄로 끝나지만, 모터는 손상된다.

**⑨ 쓰지 않는 설정을 남겨 두는 데도 비용이 있다.** "나중에 쓸지도 모르니 남기자"가 미결 항목 목록을 늘리고, 볼 때마다 같은 판단을 반복하게 만든다.
