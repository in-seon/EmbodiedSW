# 팀 인터페이스 합의 필요 사항

CLAUDE.md 6장 기준, 목표 2(쓰러짐 감지) 팀원 및 하드웨어팀과 합의가 필요한 항목.
합의되는 대로 이 문서를 갱신하고 `config/config.py`의 해당 값을 채운다.

## 신호 연장 파라미터 — **제어부로 이관됨**

프로토콜을 `ZONE <진척도>`로 단순화하면서 "얼마나 연장할지"의 판단이 전부 아두이노로
옮겨갔다(→ `docs/decisions.md` 2026-08-26). 파이는 값을 계산하지 않는다.

아두이노가 쓸 값과 근거는 `config/config.py`에 남겨 두었다 — 숫자만 스케치로 옮기면
왜 그 값인지가 사라지기 때문이다.

- [x] **기준표 `ZONE_ARRIVAL_BASE_SEC`** — `기본녹색 x (1 - (2n-1)/(2N))`.
      10초/5구역이면 `{1:9, 2:7, 3:5, 4:3, 5:1}`. "정상 속도로 걸었다면 n번째 구역에
      도착했을 때 이만큼 남아 있어야 한다"는 뜻이며, **이 표가 정상 보행 속도를 담고 있다.**
- [x] **1회 연장량 `MAX_SINGLE_EXTEND_SEC = 2`** — 낭비의 상한이 곧 이 값이다.
      근거는 설계 논리(피드백 루프 + 과잉 연장 최소화). 팀 확인 대상.
- [x] **누적 상한 `MAX_TOTAL_EXTENSION_SEC = 10`** — 강진군 "허용된 시간(5~10초)" 상한.
- [ ] **기본 녹색 `BASE_GREEN_SEC = 10`** — 실제 시연 설정과 일치시킬 것.
      이 값이 바뀌면 기준표 전체가 바뀐다.
- [ ] 잔류 확정 프레임 수 — `ZONE_RESIDENCY_FRAMES` (실측 FPS 기반). **아직 `None`이라
      `--mode full`이 막혀 있다.** 값을 정하기 전까지는 `--confirm-frames 3` 처럼 주면 돈다.

## 캘리브레이션 / 속도 추정

- [ ] **횡단보도 모형 실측 치수** — `CROSSWALK_REAL_WIDTH_CM`, `CROSSWALK_REAL_LENGTH_CM`.
      **속도와 구역 분할 둘 다에 필요하다(우선순위 높음).**
      - 없으면 속도가 px/s로만 나오고 예상 통과 시간은 계산되지 않는다.
      - 없으면 구역도 화면 기준으로 나뉘어 **실제 거리로 균등하지 않다.** 사선 구도 예시에서
        1번 77cm / 5번 429cm로 5.6배 차이가 났고, 실제 한가운데가 3번이 아닌 4번 구역에 들어갔다.
        "정중앙이면 가장 길게 연장" 규칙이 엉뚱한 위치에 적용된다는 뜻이다.
      별도의 체스보드 캘리브레이션은 필요 없다 — `tools/zone_calibrator.py`에서 네 꼭짓점을
      찍을 때 `--width-cm` / `--length-cm` 만 같이 주면 된다.
- [ ] 카메라 최종 설치 위치 고정 후 캘리브레이션 수행 (카메라를 옮기면 zone 좌표·호모그래피 모두 무효).
- [ ] 캘리브레이션 해상도와 운영 해상도 일치 확인 (다르면 좌표가 통째로 어긋난다).
- [ ] 속도 윈도우 `SPEED_WINDOW_SEC` — 사람 모형을 일정 속도로 움직여 실측 오차 확인 후 조정.
- [x] **속도·ETA는 연장 판단에서 빠졌다 — 계측용으로만 남는다.**
      기준표가 정상 보행 속도를 담고 있어 파이가 속도를 잴 필요가 없어졌다. 그 결과
      **최소 프레임률(4fps) 요구가 사라져 파이가 3fps여도 정상 동작한다.**
      `src/speed.py`는 지우지 않았다 — 도구 화면과 발표 자료용 계측으로 계속 쓴다.
- [ ] 속도 계측 정확도 확인 (발표 자료용) — 모형을 일정 속도로 움직여
      `manual_camera_person_check.py`의 `cm/s` 값이 실제와 맞는지 본다. **연장 동작에는
      영향이 없으므로 급하지 않다.**

## 교통약자 우선 연장 — **별도 처리가 불필요해짐**

기준표 방식에서는 **느린 사람이 기준 대비 지연으로 자동 검출되어 더 연장받는다.**
"휠체어인가"를 알 필요 없이 "느린가"만 보면 되고, 그건 이 방식이 자동으로 잰다.
별도 가중치도, 추가 추론도, 우선 연장 맵도 필요 없다.

`MobilityAidDetector`는 남아 있지만 **연장 판단에 쓰이지 않는다** — 화면 표시와
발표 자료용 계측이다(`FrameResult.mobility_aid_count`).

- [ ] 보조 모델을 계속 돌릴지 결정 — 추론 비용이 있으므로, 계측이 필요 없으면
      `MOBILITY_AID_MODEL_PATH = None`으로 끄면 된다.

## 하드웨어 / 통신 — **아두이노 계약**

- [ ] **제어부/구동부 보드 구성 확정** — ESP32 + 아두이노 우노는 **잠정안**.
      부저·신호등 LED·7세그먼트를 **한 보드**가 담당하기로 했고, 그래서 시리얼 채널도 하나다.

### 역할 분담 — 각자 자기만 아는 것을 판단한다

| | 아는 것 | 판단하는 것 |
|---|---|---|
| **라즈베리파이** | 영상, 사람 위치, 진입 방향 | 잔류 확정, 쓰러짐 확정, **가장 덜 건넌 사람이 몇 번째인가** |
| **아두이노** | 잔여 녹색 시간(7세그먼트) | **얼마나 연장할까**, 누적 상한, 사이클 리셋, 부저/LED |

"이 구역에 도착했을 때 몇 초 남아 있어야 정상인가"는 카운트다운을 소유한 쪽만 답할 수
있고, "이 사람이 몇 번째 구역에 있는가"는 영상을 보는 쪽만 답할 수 있다.

### 프로토콜 (확정)

개행으로 끝나는 ASCII 한 줄. `SERIAL_BAUDRATE = 9600`.

| 파이 → 아두이노 | 의미 |
|---|---|
| `NORMAL` | 횡단보도에 확정 보행자가 없음 |
| `ZONE <1..5>` | 가장 덜 건넌 사람의 **진척도**. 1 = 방금 진입, 5 = 거의 다 건넜음 |
| `FALL` | 쓰러짐 확정 |
| `PING` | 연결 확인 |

| 아두이노 → 파이 | 의미 |
|---|---|
| `READY` | 부팅 완료 (파이가 이걸 기다린 뒤 전송을 시작한다) |
| `PONG` | `PING`에 대한 답 |

**⚠️ 상태 메시지(`NORMAL`/`ZONE`/`FALL`)에는 응답하지 말 것.** 13바이트를 9600bps로
내보내는 데 13.5ms가 걸린다. 초당 여러 번이면 그 송신 시간에 아두이노 루프가 묶이고,
TX 버퍼(64B)가 차면 `Serial.print`가 아예 블로킹된다. `PING`에만 답하면 된다.

### ⚠️ `ZONE` 뒤의 숫자는 **진척도**다 — 물리 구역 번호가 아니다

구역 번호를 그대로 보내면 진입 방향에 따라 의미가 뒤집힌다. 물리적으로 같은 2번이라도
한쪽에서 온 사람은 대부분 남았고 반대쪽에서 온 사람은 거의 다 건넜다. **파이가 track별
진입 방향을 보정해서** 항상 "1 = 방금 진입, 5 = 거의 다 건넜음"으로 통일해 보낸다.

여러 명이면 **가장 작은 값**(가장 덜 건넌 사람)이 온다. 기준표가 단조 감소이므로 그
사람이 항상 가장 부족하고, 나머지는 볼 필요가 없다.

### 아두이노가 구현해야 할 것

- [ ] **기준표 — 하드코딩하지 말고 계산할 것**

      ```c
      const int  GREEN = 10;     // 기본 보행 녹색(초)
      const int  N     = 5;      // 구역 개수
      float base(int n) { return GREEN * (1.0 - (2.0*n - 1) / (2.0*N)); }
      // 10초/5구역 -> 9, 7, 5, 3, 1
      ```

      뜻: "정상 속도로 걸었다면 n번째 구역에 도착했을 때 이만큼 남아 있어야 한다."
      **이 표가 정상 보행 속도를 담고 있어서** 파이가 속도를 잴 필요가 없다.
      느린 사람(교통약자 포함)은 기준 대비 지연이 크게 잡혀 자동으로 더 연장받는다 —
      별도의 교통약자 검출이 필요 없는 이유다.

- [ ] **판정은 '구역이 바뀐 순간'에만.** 파이는 같은 `ZONE`을 1초마다 계속 재전송한다
      (유실 복구용). 받을 때마다 판정하면 같은 구역에서 계속 연장된다.

      ```c
      if (zone != lastZone) {                       // ★ 구역이 바뀐 순간에만
          if (greenRemaining < base(zone)) {        // 뒤처졌다
              int need = MAX_SINGLE_EXTEND;         // 2초
              int room = MAX_TOTAL - totalExtended;
              if (need > room) need = room;         // 거부가 아니라 '남은 만큼'
              if (need > 0) { greenRemaining += need; totalExtended += need; }
          }
          lastZone = zone;
      }
      // 새 녹색 시작 시: totalExtended = 0; lastZone = -1;
      ```

      비교는 `<`로 할 것. 기준과 정확히 같으면 "정상"이다. `<=`면 정상 보행자에게도
      매 구역 연장이 붙는다.

- [ ] **1회 2초씩 나눠 줄 것** (`MAX_SINGLE_EXTEND_SEC`). 크게 한 번 주면 보행자가 곧바로
      횡단을 마쳐도 되돌릴 수 없다. **낭비의 상한이 곧 이 값**이다. 그리고 매 구역에서
      지연을 다시 재는 피드백 루프가 되어, 뛰어가는 사람은 다음 구역에서 지연이 줄어
      연장도 자연히 줄어든다.

- [ ] **누적 상한 10초** (`MAX_TOTAL_EXTENSION_SEC`). 강진군 사례 "허용된 시간(5~10초)".

- [ ] **무신호 워치독** — 2~3초간 아무 메시지도 안 오면 파이가 죽었거나 USB가 빠진 것이다.
      `NORMAL`로 되돌리고 부저를 끈다. 파이 하트비트가 1초라 정상 동작 중에는 발동하지 않는다.

- [ ] **`FALL` 수신 시 신호를 어떻게 할 것인가 — 팀 합의 필요.**
      부저만? 차량 신호 적색 유지? 쓰러진 사람은 스스로 못 건너므로 연장으로 해결되는
      상황이 아니고, 무한 연장은 교차 방향 차량을 막아 2차 사고를 부른다.

- [ ] **모터 제어 신호 `MOTOR <1|2|3>`** (아두이노 → 파이) — 미구현.
      1=정지, 2=일반 속도, 3=교통약자 속도. 모터는 파이 GPIO에 연결돼 있다.

### 알고 있어야 할 한계

- **서 있기만 하는 사람도 연장을 소진한다.** 잔류 확정은 "계속 보인다"까지만 보고
  "건너는 중인가"는 구분하지 않는다. 상한 10초가 막지만, 시연에서 모형을 세워둔 채
  두면 그렇게 동작한다.
- **늦게 진입한 사람에게 관대하다.** 5초 남았을 때 들어와도 기준 대비 지연으로 잡혀
  연장을 받는다. 상한이 총량을 막고, 뛰어가면 다음 구역에서 지연이 줄어 자연히 멎는다.
- **track_id가 재발급되면 진입 방향을 잃는다.** 그때 파이는 중앙값으로 간주하고
  이후 이동으로 다시 확정한다. 오판은 항상 '덜 왔다'고 보는 쪽 = 더 연장하는 쪽이다.
